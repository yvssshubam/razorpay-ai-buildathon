escalation priced at CONTEST_COST + HUMAN_REVIEW_COST.
Holdout: data/holdout.jsonl (n=800). Calibrated classifier, AUC 0.800, ECE 0.0285.

One constant varied at a time; the other three held at their defaults. Both the
decision path (generator/distributions.py) and the scoring path
(eval/distributions_ref.py) are patched, since they are separate modules. An
earlier version of this sweep patched only the decision path and reported a
robust result while measuring nothing; see git history.

READING THE RESULT
------------------
The agent wins everywhere, but the more useful finding is the difference in
SENSITIVITY. The agent escalates 38 packets; contest-all escalates 316.

  HUMAN_REVIEW_COST  Rs 300 -> Rs 2500 (8x)
    agent        549,581 -> 511,300    (-7.0%)
    contest_all  451,402 -> -243,798   (turns negative at 1800)

  HUMAN_RESOLVE_RATE  0.2 -> 0.8 (4x)
    agent        508,338 -> 526,279    (+3.5%)
    contest_all  203,586 -> 293,402    (+44.1%)

Contest-all turns negative in three of the four sweeps: at CONTEST_COST 900,
at HUMAN_REVIEW_COST 1800, and at NET_RECOVERY_FRACTION 0.5. The agent never
does; its worst value anywhere is Rs 265,658.

These four constants were chosen, not measured. The point of the sweep is that
the ordering does not depend on having chosen them correctly -- and that the
agent's rupee figure is far less exposed to them than contest-all's is. Where
the true values are unknown, that stability is itself the argument.

NET_RECOVERY_FRACTION behaves as expected: the margin compresses as recovery
improves (279,516 at 0.5 down to 225,431 at 1.0), because full recovery makes
indiscriminate contesting more attractive. Note that this constant is the share
recovered GIVEN a win -- not the portfolio net-recovery figure quoted in
industry reports, which already contains the win rate and is not comparable
to it.

A fifth constant, AMOUNT_MEDIAN, is NOT swept here: varying it requires
regenerating the datasets and retraining rather than rescoring. It is disclosed
as a stated assumption in the README instead.


WHAT CHANGED SINCE THE PREVIOUS RUN
-----------------------------------
The EV rule previously priced a blocked packet at HUMAN_REVIEW_COST alone,
while eval/metrics.py charged CONTEST_COST + HUMAN_REVIEW_COST for the same
case. The agent escalated whenever gross recovery cleared Rs 1,000; the scorer
only profited above Rs 1,312.50. Every case in that band was escalated by the
policy and booked as a loss by the metric.

Correcting it moved the headline from Rs 529,555 to Rs 526,279 -- 0.6% lower on
this sample, because twelve of the repriced cases happened to be rescued and
won. Everything structural improved: escalations fell from 50 to 38, the agent's
figure rose at every contest cost above the default, and the sensitivity gap
widened. The escalation cost now has a single definition in
eval/metrics.py::escalation_cost which both the decision and scoring paths
import.
